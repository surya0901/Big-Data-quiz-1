Pipeline order and where data livesMemorizeOn quiz

Input splitsMapCombinePartitionShuffle + SortReduceOutput → HDFS
  • Map input and reduce output live in HDFS.
  • Map output (intermediate data) goes to the map node's local disk. It is temporary and never stored in HDFS.
  • Reducers copy their data from every mapper over the network (a remote read).
  • Barrier: copying can start early, but reduce() runs only after all maps finish, because an unfinished mapper may still emit that key.

How many mappers and reducersMemorizeOn her formula sheetOn quiz

#mappers = #input splits = ceil(file size / block size) block = 128 MB (64 MB in Hadoop 1 / GFS) #reducers = set by the user, default 1, can be 0 0 = map-only, straight to HDFS, no shuffle rule of thumb: 0.95 or 1.75 × (nodes × containers per node) 0.95 → every reducer launches at once 1.75 → fast nodes run a second wave, better load balance

CombinerMemorizeOn quiz

  • A mini reducer that runs on the map node, on that mapper's local output only. It saves network bandwidth.
  • The reducer can be the combiner only if the operation is commutative and associative: yes sum, count, max, min, top K. no mean, median, rank.
  • Mean trick: the combiner emits ⟨sum, count⟩ and only the reducer divides. Counterexample: (100, 90) and (80) average to 87.5, but the real answer is 90.
  • Optional: Hadoop may run it 0, 1 or many times, so the answer must be correct without it.

SortingMemorizeOn quiz

  • When: map side quicksort, then reduce side merge sort of the runs from all mappers.
  • By key only. Values arrive in any order (secondary sort orders them).
  • Purpose: group every value for a key into (k, list(v)) and hand each reducer its keys in sorted order.
  • Sort for free: make the field you want sorted the key.

PartitionerMemorizeOn quiz

  • Decides which reducer gets each key. Default hash(key) % R. Same key always goes to the same reducer.
  • Global sort across several reducers needs a range partitioner, because hashing scrambles order.
  • A bad partitioner causes skew: one overloaded reducer while others sit idle.

StragglersMemorizeOn quiz

Slow tasks (bad disk, network, CPU, memory). Because of the barrier they slow the whole job. Fix: speculative execution. Run backup copies, keep the first to finish, kill the rest.

YARNMemorizeOn quiz

Yet Another Resource Negotiator (Hadoop 2.0). Manages cluster resources separately from MapReduce. Each server is split into containers of fixed CPU and memory.

ComponentHow manyWhat it does
Resource Manager (RM)1, globalSchedules. Restarts a failed AM
Node Manager (NM)1 per serverRuns tasks, sends heartbeats to the RM
Application Master (AM)1 per jobNegotiates containers, detects task failures

Descriptive templateMemorizeOn quiz

Map(key, value){ // key: ... value: ... Emit(<group-by or sort-by field>, <what you need>); } Reduce(key, list of values){ // key: ... values: ... Emit(key, <aggregate>); }

Always say whether a combiner works and why. If one round can't do the job, write Round 2.

Utilization ratio (RI)On her formula sheetMaybe on quiz

  1. Mappers = ceil(size / 128). Reducers = given factor × mappers.
  2. Active reducers ≤ number of different values the hash expression can produce (% 10 gives 10, % 10 on odd numbers gives only 5).
  3. RI = active reducers / active mappers. For a target %, solve r / m = target with r under that cap.

Her example: 15 shards → 15 maps, 18 reducers, % 10 → at most 10 active. Max 10/15 ≈ 66.7%, min 1/15 ≈ 6.7%, 40% = 6/15.

Practice problems

P1. Min and max per cityOn quiz

Sensor records sensorID::city::timestamp::temp. Output, for each city, the minimum and maximum temperature. Can the reducer also be the combiner?

Answer
Map: Emit(city, (temp, temp)) // (min, max) Reduce: Emit(city, (min of all mins, max of all maxes))

Yes. Min and max are commutative and associative, so the min of local mins is the global min, and likewise for max.

P2. Document frequencyOn quiz

Input (docID, text). For each word, output the number of distinct documents that contain it. What mistake would give the wrong count?

Answer
Map: for each DISTINCT word w in text: Emit(w, 1) Reduce: Emit(w, sum(values))

The mistake is emitting once per occurrence: a word appearing 5 times in one document would count as 5 documents. A sum combiner works fine.

P3. Users who watched exactly k moviesOn quiz

Records (userID, movieID), no duplicates. For each k, output how many users watched exactly k movies.

Answer
Round 1: Map: Emit(userID, 1) Reduce: Emit(userID, sum) // k per user Round 2: Map: (userID, k) → Emit(k, 1) Reduce: Emit(k, sum)

A sum combiner works in both rounds.

P4. Followers you don't follow backOn quiz

Lines (a, b) mean a follows b. For each user, list the people who follow them but whom they don't follow back.

Answer
Map: Emit(b, ("IN", a)); Emit(a, ("OUT", b)) Reduce: (U, values) → followers = { x : ("IN", x) } following = { y : ("OUT", y) } Emit(U, followers − following)

No combiner, because the reducer needs the actual user IDs.

P5. UtilizationMaybe on quiz

P6. Combiner judgmentOn quiz

Can the reducer be the combiner? (a) Total sales per store (b) Median salary per department (c) Top 3 scores per student (d) Average rating per movie (e) Count of words per document

Answer
  • (a) yes sum. (b) no median of medians isn't the median. (c) yes local top 3, then top 3 of those.

P7. SkewMaybe on quiz

Counting tweets per hashtag with 4 reducers and hash partitioning. One hashtag is 50% of all tweets. What goes wrong? Two fixes.

Answer

One reducer gets at least 50% of the data and becomes a straggler. Fix 1: a sum combiner, so each mapper sends one count per hashtag. Fix 2: salt the hot key into tag#1 … tag#k, then add the partial counts in Round 2.

P8. Sort by score, highest firstOn quiz

Records (name, score), scores 0 to 100. Output names from highest to lowest score using 3 reducers. Map, Reduce, and the partitioner.

Answer
Map: Emit(100 − score, name) Reduce: for each n in values: Emit(n, 100 − key)

Range partitioner: reducer 0 gets keys 0 to 33, reducer 1 gets 34 to 66, reducer 2 gets 67 to 100. Reading part-0, part-1, part-2 in order gives the full descending order. Hashing would break it.

P9. Short answerOn quiz

(a) Combiner or shuffle first? (b) What if reducers = 0? (c) Can reduce() start before all maps finish? (d) Why is map output on local disk, not HDFS? (e) Which YARN component restarts a failed AM?

Answer
  • (a) Combiner, on the map node, before the shuffle.
  • (b) Map-only job: no shuffle or sort, output straight to HDFS.
  • (c) No. Copying can start early, but reduce() waits at the barrier.
  • (d) It's temporary. Replicating it wastes bandwidth, and a failed map is simply rerun.
  • (e) The Resource Manager.

P10. Multiple choiceOn quiz

Values arriving at a reducer are… (i) sorted ascending (ii) sorted descending (iii) in no guaranteed order (iv) sorted by the partitioner

Answer

(iii) Only the keys are sorted.

P11. HW2 P1: sort values descending, no sort instructionOn quiz

Records (key, value), value in [0, N]. Sort the values in descending order automatically, without any sort instruction.

Answer
Map: Emit(N − value, key) Reduce: for each k in values: Emit(k, N − key)

The framework sorts keys ascending, so N − value ascending = value descending. One reducer gives one sorted file. With several reducers, use a range partitioner.

P12. HW2 P2: babies per month, A to M and N to ZOn quiz

40 M records, mapper (month, 1), reducer sums. Reducer 1 gets keys A to M, Reducer 2 gets N to Z. What goes wrong? Give numbers and a fix.

Answer

9 months start A to M, only 3 (Sep, Oct, Nov) start N to Z. By days: 274/365 ≈ 75% → about 30 M records to Reducer 1, about 10 M to Reducer 2. Reducer 1 does 3× the work and becomes a straggler. No combiner means all 40 M pairs cross the network. Only 12 keys, so at most 12 reducers help.

Fix: a sum combiner (each mapper sends at most 12 pairs), a balanced partitioner (6 months each), or up to 12 reducers.

Conceptual answers

These are the exact questions from her announcement. A strong answer says what the piece is, when it runs, what it is for, and its limits. Try each one before opening it.

1. What is the role of a combiner, and when can it be used?

A combiner is a mini reducer that runs on the mapper node after the map phase, on that mapper's local output only. It pre-aggregates values with the same key so far less data crosses the network in the shuffle. Word count example: three (hello,1) pairs become one (hello,3).

It can be used when partial aggregation gives the same final answer, which means the operation is commutative and associative. It is optional: Hadoop may run it zero, one or several times, so the job must be correct without it, and its output type must match the map output type.

2. When is the combiner similar to the reducer, and when not?

Same as the reducer: for distributive operations such as sum, count, max, min and top K. Example: max temperature per year. The combiner keeps each mapper's max and the reducer takes the max of maxes.

Not the same: for non-distributive operations such as mean, median and rank. An average of averages is wrong when groups differ in size: (95 + 80)/2 = 87.5 instead of 90. The fix is a different combiner that emits <sum, count> while the reducer adds those and divides. Also not the same when the reducer needs the raw values (common friends needs the full lists).

3. What is the role of sorting? When does it happen and what does it aim at?

When: between map and reduce, as part of shuffle and sort. Map output is sorted by key on the map node (quicksort, fast and low memory). Each reducer then merge sorts the sorted runs it fetched from all mappers (merge sort is the default, since the data comes from different nodes).

Aim: to group all values of a key together so reduce can be called once per key with (k, list(v)), and to hand keys to each reducer in sorted order.

Limits: it sorts by key only. Values arrive in any order, so secondary sort is needed to order them. A global sort with many reducers needs a range partitioner. You can exploit it: make the field you want sorted the key (HW2 P1, WordCount 2).

4. What is the partitioner?

The function that decides which reducer receives each intermediate key. It takes (key, number of reducers) and returns a reducer index, so n partitions means n reducers, and all values for one key reach the same reducer. The default is HashPartitioner, hash(key) % R. Custom partitioners can route by meaning (gender, flight number) or by ranges for a total order sort. A poor choice causes skew and idle reducers, as in HW2 P2 and P3.

5. What is the order of the tasks in MapReduce?
SplitMapCombinePartitionShuffle + SortReduceWrite

The user program forks a master and workers. The master assigns map and reduce tasks. Map workers read their split, run map, optionally combine, partition, and write to local disk. Reduce workers remote read their partitions, merge sort by key, wait at the barrier until all maps finish, run reduce, and write one output file each to the DFS.

6. How many mappers do we have? How many reducers?

Mappers: one per input split, so it depends on the number of HDFS blocks: ceil(file size / block size), with 128 MB blocks by default in Hadoop 2 and 3. Change the block size to change the number of maps. Aim for 10 to 100 per node, each running at least a minute.

Reducers: chosen by the user, default 1, can be 0. Rule of thumb 0.95 or 1.75 × (nodes × max containers per node). Only reducers that some key is partitioned to are active, so the hash can cap the useful number below the configured one.

7. What are stragglers?

Tasks that run much slower than their peers because of a bad disk, network bandwidth, CPU or memory. Because reduce waits at the barrier for every map, one straggler delays the whole job. MapReduce tracks each task's progress and launches backup copies of the slow ones (speculative execution). The first copy to finish counts and the rest are killed.

8. What is YARN?

Yet Another Resource Negotiator, the resource management layer added in Hadoop 2.0. It separates managing cluster resources from the MapReduce framework, so other frameworks can share the cluster. Servers are divided into containers of fixed CPU and memory. The global Resource Manager schedules. Each server's Node Manager runs and tracks its tasks and heartbeats to the RM. Each job's Application Master negotiates containers and detects task failures.

9. Why does reduce wait for every map task?

An unfinished mapper may still produce a value for any key, so a reducer cannot know it has the complete list for a key until all maps are done. Copying (the shuffle) may start early as maps finish, but the user reduce() function waits for the barrier.

10. Why is map output written to local disk and not HDFS?

It is temporary. Replicating it three times in HDFS would waste bandwidth and disk. If the map node fails before reducers copy its output, the map task is simply rerun. Only the final reduce output is written to the DFS, where it is replicated.

Problem 1. Employee salaries

A large file has one record per line: employeeID::department::salary.

(a) [descriptive] Using highly descriptive language, write Map and Reduce that output, for each department, the highest salary and the employee who earns it.

(b) [descriptive] Change the program to output the average salary per department. Write a combiner that keeps the result correct.

(c) [conceptual] In (a) can the reducer be used as the combiner? In (b)? Explain.

Solution 1

(a)

Map(key, value){ // key: line number, value: employeeID::department::salary Emit(department, (salary, employeeID)); } Reduce(key, list of values){ // key: department, values: (salary, employeeID) pairs best = the pair with the largest salary; Emit(key, best); }

(b)

Map: Emit(department, <salary, 1>) Combine: Emit(department, <Σ salary, Σ count>) Reduce: S = Σ sums; C = Σ counts; Emit(department, S / C)

(c)

(a) Yes. Max is commutative and associative, so the max of local maxes is the global max. (b) No. Mean is not distributive. Averaging local averages weights each mapper equally rather than each employee, so the answer is wrong whenever mappers hold different numbers of employees. The combiner must pass <sum, count> and only the reducer divides.

Problem 2. Course enrollment

Records are (studentID, courseID), one per enrollment, with no duplicates.

(a) [descriptive] Output, for each course, the list of students enrolled.

(b) [descriptive] Output all courses sorted from the largest enrollment to the smallest. Use as many rounds as needed and say how many reducers the last round uses.

Solution 2

(a) Same shape as the reverse web-link graph

Map: (studentID, courseID) → Emit(courseID, studentID) Reduce: (courseID, list of studentIDs) → Emit(courseID, list)

(b) Two rounds, like WordCount 2

// Round 1: count students per course (combiner = reducer, sum) Map1: Emit(courseID, 1) Reduce1: Emit(courseID, sum(values)) // Round 2: swap key and value so the shuffle sorts by size Map2: (courseID, n) → Emit(MAX - n, courseID) // or a descending comparator Reduce2: for each c in values: Emit(c, MAX - key) // identity, restore n

Use 1 reducer in round 2 so the single output file is globally sorted. With several reducers you would need a range partitioner. No explicit sort is written: the shuffle and sort phase does it.
