1. Pipeline order and where data lives

Input splitsMapCombinePartitionShuffle + SortReduceOutput → HDFS
  • Map input and reduce output live in HDFS.
  • Map output (intermediate data) goes to the map node's local disk. It is temporary and never stored in HDFS.
  • Reducers copy their data from every mapper over the network (a remote read).

2. The barrier

Reducers can start copying early, but reduce() runs only after all maps finish, because an unfinished mapper might still emit a value for that key.

3. How many mappers and reducers

#mappers = #input splits = ceil(file size / block size) block = 128 MB (64 MB in Hadoop 1 / GFS) #reducers = set by the user, default 1, can be 0 0 = map-only, straight to HDFS, no shuffle rule of thumb: 0.95 or 1.75 × (nodes × containers per node) 0.95 → every reducer launches at once 1.75 → fast nodes run a second wave, better load balance

4. Combiner

  • A mini reducer that runs on the map node, on that mapper's local output only. Its job is to save network bandwidth.
  • The reducer can double as the combiner only if the operation is commutative and associative.
    • yes sum, count, max, min, top K
    • no mean, median, rank
  • For a mean, the combiner emits ⟨sum, count⟩ and only the reducer divides.
  • Optional: Hadoop may run it 0, 1 or many times, so the answer must be correct without it.

5. Sorting

  • Map side: output sorted with quicksort. Reduce side: sorted runs from all mappers are merge sorted.
  • Sorting is by key only. Values arrive in any order (use secondary sort to order them).
  • Purpose: group every value for a key, giving (k, list(v)), and hand each reducer its keys in sorted order.
  • Trick to sort for free: make the field you want sorted the key.

6. Partitioner

  • Decides which reducer gets each key. Default hash(key) % R. Same key always goes to the same reducer.
  • Global sort across several reducers needs a range partitioner, because hashing scrambles order.
  • A bad partitioner causes skew: one overloaded reducer while others sit idle.

7. Stragglers

Slow tasks (bad disk, network, CPU, memory). Because of the barrier they slow the whole job. Fix: speculative execution. Run backup copies, keep the first to finish, kill the rest.

8. YARN

Manages cluster resources separately from MapReduce (Hadoop 2.0). Each server is split into containers of fixed CPU and memory.

ComponentHow manyWhat it does
Resource Manager (RM)1, globalSchedules
Node Manager (NM)1 per serverRuns tasks, sends heartbeats to the RM
Application Master (AM)1 per jobNegotiates containers, detects task failures

9. Utilization recipe (RI)

  1. Mappers = ceil(size / 128).
  2. Reducers = given factor × mappers.
  3. Active reducers ≤ number of different values the hash expression can produce (% 10 gives 10, % 10 on odd numbers gives only 5).
  4. RI = active reducers / active mappers.
  5. For a target %, solve r / m = target with r under that cap.

10. Template for the descriptive problems

Map(key, value){ // key: ... value: ... Emit(<group-by or sort-by field>, <what you need>); } Reduce(key, list of values){ // key: ... values: ... Emit(key, <aggregate>); }

Always say whether a combiner works and why. If one round can't do the job, write Round 2.

10 practice problems

Try each on paper, then open the answer.

P1. Min and max per city [descriptive]

Sensor records sensorID::city::timestamp::temp. Output, for each city, the minimum and maximum temperature. Can the reducer also be the combiner?

Answer
Map: Emit(city, (temp, temp)) // (min, max) Reduce: Emit(city, (min of all mins, max of all maxes))

Yes. Min and max are commutative and associative, so the min of local mins is the global min, and likewise for max.

P2. Document frequency [descriptive]

Input (docID, text). For each word, output the number of distinct documents that contain it. What mistake would give the wrong count?

Answer
Map: for each DISTINCT word w in text: Emit(w, 1) Reduce: Emit(w, sum(values))

The mistake is emitting once per occurrence instead of once per document: a word appearing 5 times in one document would count as 5 documents. A sum combiner works fine.

P3. How many users watched exactly k movies [descriptive, two rounds]

Records (userID, movieID), one per movie a user watched, no duplicates. For each k, output how many users watched exactly k movies.

Answer
Round 1: Map: Emit(userID, 1) Reduce: Emit(userID, sum) // k per user Round 2: Map: (userID, k) → Emit(k, 1) Reduce: Emit(k, sum)

A sum combiner works in both rounds.

P4. Followers you don't follow back [descriptive]

Lines (a, b) mean a follows b. For each user, output the list of people who follow them but whom they don't follow back.

Answer
Map: Emit(b, ("IN", a)); Emit(a, ("OUT", b)) Reduce: (U, values) → followers = { x : ("IN", x) } following = { y : ("OUT", y) } Emit(U, followers − following)

No combiner, because the reducer needs the actual user IDs, not counts.

P5. Utilization [quantitative]

A 3000 MB file is sharded with Hadoop defaults. Reducers = 0.5 × map tasks. The partition is hash(K) % 5. (a) How many mappers and reducers? (b) Highest and lowest RI? (c) When is RI exactly 12.5%?

Answer
(a) 3000 / 128 = 23.4 → 24 mappers; 0.5 × 24 = 12 reducers (b) % 5 gives only 0..4 → at most 5 active reducers max RI = 5/24 ≈ 20.8% keys hit all five values min RI = 1/24 ≈ 4.2% every key hashes to the same value (c) 3/24 = 12.5% all 24 maps running, keys hash to exactly 3 values

P6. Combiner judgment [conceptual]

Can the reducer be used as the combiner? (a) Total sales per store (b) Median salary per department (c) Top 3 scores per student (d) Average rating per movie (e) Count of words per document

Answer
  • (a) yes It's a sum.
  • (b) no The median of medians isn't the median.
  • (c) yes Keep a local top 3, then the top 3 of those.
  • (d) no Combiner must pass ⟨sum, count⟩, only the reducer divides.
  • (e) yes It's a sum.

P7. Skew [conceptual]

Counting tweets per hashtag with 4 reducers and hash partitioning. One hashtag makes up 50% of all tweets. What goes wrong? Give two fixes.

Answer

Every tweet with the hot hashtag goes to one reducer, which gets at least 50% of the data and becomes a straggler.

  • Fix 1: a sum combiner, so each mapper sends just one count per hashtag.
  • Fix 2: salt the hot key into tag#1 … tag#k so it spreads across reducers, then add up the partial counts in Round 2.

P8. Sort by score, highest first [descriptive]

Records (name, score), scores 0 to 100. Output names sorted by score from highest to lowest using 3 reducers. Write Map and Reduce and name the partitioner.

Answer
Map: Emit(100 − score, name) Reduce: for each n in values: Emit(n, 100 − key)

Use a range partitioner: reducer 0 gets keys 0 to 33, reducer 1 gets 34 to 66, reducer 2 gets 67 to 100. Reading part-0, part-1, part-2 in order gives the full descending order. Hashing would break it.

P9. Short answer [conceptual]

(a) Which runs first, the combiner or the shuffle? (b) What happens if the number of reducers is 0? (c) Can reduce() start before all maps finish? (d) Why does map output go to local disk instead of HDFS? (e) Which YARN component restarts a failed AM?

Answer
  • (a) The combiner. It runs on the map node before the data is shuffled.
  • (b) A map-only job: no shuffle or sort, map output goes straight to HDFS.
  • (c) No. Copying can start early, but reduce() waits at the barrier.
  • (d) It's temporary. Replicating it in HDFS wastes bandwidth, and a failed map task is simply rerun.
  • (e) The Resource Manager.

P10. Multiple choice [conceptual]

Values arriving at a reducer are… (i) sorted ascending (ii) sorted descending (iii) in no guaranteed order (iv) sorted by the partitioner

Answer

(iii) In no guaranteed order. Only the keys are sorted.

MapReduce and Hadoop

The model

The terms come from functional programming: (map square '(1 2 3 4)) gives (1 4 9 16), and (reduce + '(1 4 9 16)) gives 30. Map processes each record independently, so it has implicit parallelism. Reduce merges all values for one key.

Map (k1, v1) → list(k2, v2) Reduce (k2, list(v2)) → list(v3) Combine (k2, list(v2)) → (k2, v2') optional, on the map node Partition (k2, R) → reducer index default hash(k2) % R

The programmer writes Map and Reduce and sets the number of reducers. The framework handles distribution, the shuffle, fault tolerance and storage. All values with the same key go to the same reducer.

The pipeline

Input splitsMapCombinePartitionShuffle + SortReduceOutput → HDFS
map nodebetween the phasesreduce node
  1. The InputFormat splits the input into InputSplits. A RecordReader turns each split into (k1, v1) records.
  2. Map runs per record. Its output is sorted by key in memory (quicksort) and spilled to the local disk of the map node.
  3. Combine (optional) is a mini reduce on that one mapper's output. It saves network bandwidth.
  4. Partition picks the reducer for each key.
  5. Shuffle: each reducer copies its partition from every mapper over HTTP (remote read). Sort: it merge sorts the runs by key. Shuffle and sort overlap.
  6. Barrier: user reduce() starts only after all maps finish, because an unfinished mapper may still emit the same key.
  7. Reduce runs once per key and writes to the DFS. R reducers give R output files, which can feed the next round.

Google paper numbering: (1) fork, (2) master assigns map and reduce, (3) read split, (4) local write, (5) remote read, (6) write output.

Where the data lives

DataLocation
Map inputDistributed file system (HDFS or GFS)
Map output (intermediate)Local disk of the map node. Transient, never in HDFS
Reduce inputRemote reads from many map nodes' local disks
Reduce outputDistributed file system

Counting mappers and reducers

#maps = #input splits = ceil(file size / block size) block size: 128 MB default in Hadoop 2 and 3 (64 MB in Hadoop 1 and GFS) #reducers = set by the user, default 1, Job.setNumReduceTasks(int), may be 0 rule of thumb: 0.95 or 1.75 × (nodes × max containers per node) active reducers ≤ min(#reducers, #distinct partition values the hash can produce) RI (utilization) = #active reducers / #active mappers

Good map parallelism is 10 to 100 maps per node, each running at least about a minute since setup is costly. With 0.95, all reducers launch at once and copy as maps finish. With 1.75, fast nodes run a second wave, which balances load better. Zero reducers means a map-only job whose output goes straight to HDFS.

Combiner

Runs on the mapper node after the map phase, on local output only. (hello,1)(hello,1)(hello,1) becomes (hello,3) before the shuffle. Hadoop may run it zero, one or many times, so correctness must not depend on it.

Distributive (reducer can be combiner)Non-distributive (it cannot)
sum, count, min, max, top Kmean, median, rank

Her average trick (Extra Examples): temps 100 and 90 on one mapper, 80 on another. Averaging in the combiner gives (95 + 80)/2 = 87.5, but the real answer is 270/3 = 90. Fix: the combiner emits <sum, count> and the reducer divides Σsum by Σcount.

Sorting

  • When: map side (quicksort of the buffered map output) and reduce side (merge sort of runs from many mappers, the default).
  • What it aims at: grouping every value for a key so reduce gets (k, list(v)). Keys arrive at every reducer sorted.
  • Values are not sorted. Use secondary sort (value to key conversion) if you need that.
  • With one reducer the output is fully sorted. With many, each file is sorted, and a global order needs a range partitioner, since hashing scrambles order.

Partitioner

Divides the intermediate key space among reducers: n partitions means n reducers. It takes the key and the number of reducers and returns an index. The default is HashPartitioner. Custom ones are possible, like her Male → 0, Female → 1 example and the flight number example. A poor partitioner causes skew (one overloaded reducer) and idle reducers.

Stragglers and fault tolerance

Stragglers are slow tasks from a bad disk, network bandwidth, CPU or memory. Because of the barrier the slowest task slows the whole job. Hadoop tracks each task's progress and runs backup copies of stragglers. The first copy to finish wins and the others are killed. This is speculative execution.

Locality: HDFS stores 3 replicas, 2 on one rack and 1 on another. Maps are scheduled on a node with a replica, else on the same rack, else anywhere.

YARN

Yet Another Resource Negotiator, from Hadoop 2.0 (2012). It splits cluster resource management away from MapReduce and treats each server as a set of containers (fixed CPU plus fixed memory).

ComponentHow manyJob
Resource Manager (RM)One, globalScheduling
Node Manager (NM)One per serverDaemon and server functions, tracks tasks on its server, heartbeats to RM
Application Master (AM)One per jobNegotiates containers with RM and NMs, detects task failures

Getting a container: (1) AM asks the RM, (2) a container finishes and its NM reports it, (3) RM gives the AM a container on that node, (4) AM tells that NM to start the task. If a server fails, the RM times out on its heartbeat and tells the affected AMs. If an AM fails, the RM restarts it. If the RM fails, a secondary RM comes up from checkpoints.

Hadoop in Java (lighter weight for the quiz)

A job has a driver (sets mapper, reducer, partitioner, combiner, number of reducers), a Mapper class and a Reducer class. Keys implement WritableComparable, values implement Writable. TextInputFormat gives (byte offset, line). KeyValueTextInputFormat splits a line at the tab. Hadoop Streaming lets you write Map and Reduce in any language through stdin and stdout.

Conceptual answers

These are the exact questions from her announcement. A strong answer says what the piece is, when it runs, what it is for, and its limits. Try each one before opening it.

1. What is the role of a combiner, and when can it be used?

A combiner is a mini reducer that runs on the mapper node after the map phase, on that mapper's local output only. It pre-aggregates values with the same key so far less data crosses the network in the shuffle. Word count example: three (hello,1) pairs become one (hello,3).

It can be used when partial aggregation gives the same final answer, which means the operation is commutative and associative. It is optional: Hadoop may run it zero, one or several times, so the job must be correct without it, and its output type must match the map output type.

2. When is the combiner similar to the reducer, and when not?

Same as the reducer: for distributive operations such as sum, count, max, min and top K. Example: max temperature per year. The combiner keeps each mapper's max and the reducer takes the max of maxes.

Not the same: for non-distributive operations such as mean, median and rank. An average of averages is wrong when groups differ in size: (95 + 80)/2 = 87.5 instead of 90. The fix is a different combiner that emits <sum, count> while the reducer adds those and divides. Also not the same when the reducer needs the raw values (common friends needs the full lists).

3. What is the role of sorting? When does it happen and what does it aim at?

When: between map and reduce, as part of shuffle and sort. Map output is sorted by key on the map node (quicksort, fast and low memory). Each reducer then merge sorts the sorted runs it fetched from all mappers (merge sort is the default, since the data comes from different nodes).

Aim: to group all values of a key together so reduce can be called once per key with (k, list(v)), and to hand keys to each reducer in sorted order.

Limits: it sorts by key only. Values arrive in any order, so secondary sort is needed to order them. A global sort with many reducers needs a range partitioner. You can exploit it: make the field you want sorted the key (HW2 P1, WordCount 2).

4. What is the partitioner?

The function that decides which reducer receives each intermediate key. It takes (key, number of reducers) and returns a reducer index, so n partitions means n reducers, and all values for one key reach the same reducer. The default is HashPartitioner, hash(key) % R. Custom partitioners can route by meaning (gender, flight number) or by ranges for a total order sort. A poor choice causes skew and idle reducers, as in HW2 P2 and P3.

5. What is the order of the tasks in MapReduce?
SplitMapCombinePartitionShuffle + SortReduceWrite

The user program forks a master and workers. The master assigns map and reduce tasks. Map workers read their split, run map, optionally combine, partition, and write to local disk. Reduce workers remote read their partitions, merge sort by key, wait at the barrier until all maps finish, run reduce, and write one output file each to the DFS.

6. How many mappers do we have? How many reducers?

Mappers: one per input split, so it depends on the number of HDFS blocks: ceil(file size / block size), with 128 MB blocks by default in Hadoop 2 and 3. Change the block size to change the number of maps. Aim for 10 to 100 per node, each running at least a minute.

Reducers: chosen by the user, default 1, can be 0. Rule of thumb 0.95 or 1.75 × (nodes × max containers per node). Only reducers that some key is partitioned to are active, so the hash can cap the useful number below the configured one.

7. What are stragglers?

Tasks that run much slower than their peers because of a bad disk, network bandwidth, CPU or memory. Because reduce waits at the barrier for every map, one straggler delays the whole job. MapReduce tracks each task's progress and launches backup copies of the slow ones (speculative execution). The first copy to finish counts and the rest are killed.

8. What is YARN?

Yet Another Resource Negotiator, the resource management layer added in Hadoop 2.0. It separates managing cluster resources from the MapReduce framework, so other frameworks can share the cluster. Servers are divided into containers of fixed CPU and memory. The global Resource Manager schedules. Each server's Node Manager runs and tracks its tasks and heartbeats to the RM. Each job's Application Master negotiates containers and detects task failures.

9. Why does reduce wait for every map task?

An unfinished mapper may still produce a value for any key, so a reducer cannot know it has the complete list for a key until all maps are done. Copying (the shuffle) may start early as maps finish, but the user reduce() function waits for the barrier.

10. Why is map output written to local disk and not HDFS?

It is temporary. Replicating it three times in HDFS would waste bandwidth and disk. If the map node fails before reducers copy its output, the map task is simply rerun. Only the final reduce output is written to the DFS, where it is replicated.

P1. Sort values in descending order with no sort instruction

The framework sorts keys in ascending order, so make the value the key and flip it. Values are in [0, N], so N − value is never negative.

Map(key, value){ // key: record key, value: integer in [0, N] Emit(N - value, key); } Reduce(key, list of values){ // key: N - value, ascending = original values descending // values: original keys with that value for each k in values: Emit(k, N - key); }

One reducer gives one fully sorted file. With several reducers use a range partitioner: reducer 0 gets the smallest keys (largest values), so reading part-0, part-1, ... in order is a global descending sort. A hash partitioner would break the order.

P2. Babies per month, Reducer 1 gets A to M, Reducer 2 gets N to Z

The keys are month names. Nine months start with A to M and only three (September, October, November) with N to Z. Births are close to uniform across the year.

ReducerMonthsDaysShareRecords of 40 M
Reducer 1 (A to M)927475%≈ 30.0 M
Reducer 2 (N to Z)39125%≈ 10.0 M

Issues: Reducer 1 does 3× the work and becomes a straggler while Reducer 2 idles. With no combiner, all 40 M (month, 1) pairs cross the network. With only 12 distinct keys, at most 12 reducers can ever be useful.

Workarounds: add a combiner equal to the reducer (sum is commutative and associative), so each mapper sends at most 12 pairs. Use a balanced partitioner (6 months each, for example by month number) or up to 12 reducers.

P3. 2386 MB, reducers = 1.8 × maps, odd hash

The problem text conflicts. It says "modulo 17" and then writes "hash(K) % 10". The odd last digit only matters for % 10, so that is almost surely intended. Check her solution.

#maps = ceil(2386 / 128) = ceil(18.64) = 19 (64 MB blocks: 38) #reducers = 1.8 × 19 = 34.2 → 34 hash(K) ends in 1,3,5,7,9 → hash(K) % 10 ∈ {1,3,5,7,9} → at most 5 active reducers highest RI = 5/19 ≈ 26.3% all 5 remainders hit, all 19 maps running lowest RI = 1/19 ≈ 5.3% every key hashes to the same last digit 75%: 19 maps would need 14.25 reducers, impossible → 3 active reducers / 4 active mappers (late in the map phase, 15 maps done)

If she meant % 17: an odd number mod 17 can be any of 0 to 16, so up to 17 reducers are active. Max 17/19 ≈ 89.5%, min 1/19, and 75% is 3/4, 6/8, 9/12 or 12/16.

P4. At least 1 M followers, follows fewer than 10, all followed back

Map(key, value){ // value: (a, b) means a follows b Emit(b, ("IN", a)); // a is a follower of b Emit(a, ("OUT", b)); // a follows b } Reduce(key, list of values){ // key: user U, values: tagged followers and followees followers = { x : ("IN", x) } following = { y : ("OUT", y) } if |followers| ≥ 1,000,000 and |following| < 10 and following ⊆ followers: Emit(U, _); }

No combiner, since the reducer needs the actual IDs. To avoid holding a million IDs, use secondary sort so the at most 9 "OUT" values arrive first, then stream and count the "IN" values. Say whether a user who follows nobody counts (they pass conditions ii and iii trivially).

P5. Relative frequency of (word1, word2), word1 first

// Round 1: count ordered adjacent pairs (combiner = reducer, sum) Map1: for i in 0 .. n-2: Emit((w[i], w[i+1]), 1) Reduce1: Emit((w1, w2), sum(values)) // Round 2: regroup by word1 and divide Map2: ((w1, w2), c) → Emit(w1, (w2, c)) Reduce2: total = Σ c; for each (w2, c): Emit((w1, w2), c / total)

One round alternative: Map also emits ((w1, *), 1). A custom partitioner routes on w1 only, and the sort order puts (w1, *) first, so the reducer learns the total before it sees any (w1, w2) and can divide immediately.

Problem 1. Employee salaries

A large file has one record per line: employeeID::department::salary.

(a) [descriptive] Using highly descriptive language, write Map and Reduce that output, for each department, the highest salary and the employee who earns it.

(b) [descriptive] Change the program to output the average salary per department. Write a combiner that keeps the result correct.

Solution 1

(a)

Map(key, value){ // key: line number, value: employeeID::department::salary Emit(department, (salary, employeeID)); } Reduce(key, list of values){ // key: department, values: (salary, employeeID) pairs best = the pair with the largest salary; Emit(key, best); }

(b)

Map: Emit(department, <salary, 1>) Combine: Emit(department, <Σ salary, Σ count>) Reduce: S = Σ sums; C = Σ counts; Emit(department, S / C)

(c)

(a) Yes. Max is commutative and associative, so the max of local maxes is the global max. (b) No. Mean is not distributive. Averaging local averages weights each mapper equally rather than each employee, so the answer is wrong whenever mappers hold different numbers of employees. The combiner must pass <sum, count> and only the reducer divides.

Problem 2. Course enrollment

Records are (studentID, courseID), one per enrollment, with no duplicates.

(a) [descriptive] Output, for each course, the list of students enrolled.

(b) [descriptive] Output all courses sorted from the largest enrollment to the smallest. Use as many rounds as needed and say how many reducers the last round uses.

Solution 2

(a) Same shape as the reverse web-link graph

Map: (studentID, courseID) → Emit(courseID, studentID) Reduce: (courseID, list of studentIDs) → Emit(courseID, list)

(b) Two rounds, like WordCount 2

// Round 1: count students per course (combiner = reducer, sum) Map1: Emit(courseID, 1) Reduce1: Emit(courseID, sum(values)) // Round 2: swap key and value so the shuffle sorts by size Map2: (courseID, n) → Emit(MAX - n, courseID) // or a descending comparator Reduce2: for each c in values: Emit(c, MAX - key) // identity, restore n

Use 1 reducer in round 2 so the single output file is globally sorted. With several reducers you would need a range partitioner. No explicit sort is written: the shuffle and sort phase does it.

Problem 3. Concepts

(a) [quantitative] Hadoop shards a 1500 MB document using defaults. Reducers = 2 × map tasks. The partitioner is hash(K) % 6. Find the number of mappers and reducers, the highest and lowest utilization ratio (active reducers / active mappers), and a scenario where it is exactly 25%.

Input splits, map, combine, partition, shuffle and sort, reduce, output to HDFS. Map output goes to the local disk of the map node, not HDFS.

(c)

A task much slower than its peers (bad disk, network, CPU or memory). Because of the barrier it delays the whole job. Hadoop launches backup copies (speculative execution), keeps the first to finish and kills the rest.

(iii) Application Master.

(e)

False. Keys arrive sorted and grouped, but the values for a key can be in any order. Secondary sort (value to key conversion) is needed to order them.

Extra drills

Short problems in the style of the Extra Examples deck and HW2. Do each in under 3 minutes.

D1. Inverted index

Input (docID, text). Output each word with the sorted list of distinct docIDs that contain it.

Answer
Map: for each distinct word w in text: Emit(w, docID) Reduce: Emit(w, sort(unique(values)))

Values are not sorted by the framework, so sort them in the reducer or use secondary sort. A duplicate removing combiner is safe since set union is commutative and associative.

D2. Mutual follows

Lines (a, b) mean a follows b, no duplicates. Output every pair that follows each other, once.

Answer
Map: Emit((min(a,b), max(a,b)), 1) Reduce: if sum(values) == 2: Emit(key, _)

Sorting the pair sends a→b and b→a to the same key, the same trick as common friends. A sum combiner is fine.

D3. Utilization

1000 MB file, defaults. Reducers = 1.5 × maps. The hash always returns an even number, partition is hash(K) % 8. Highest and lowest RI? When is it 25%?

Answer
#maps = ceil(1000 / 128) = 8, #reducers = 12 even % 8 ∈ {0, 2, 4, 6} → at most 4 active highest 4/8 = 50%, lowest 1/8 = 12.5%, 25% = 2/8 (keys hit 2 remainders)

D4. How many reducers?

A cluster has 20 nodes with up to 8 containers each. Give both rule of thumb reducer counts and say what each one achieves.

Answer

20 × 8 = 160 containers. 0.95 × 160 = 152: every reducer launches at once and starts copying as maps finish. 1.75 × 160 = 280: fast nodes run a second wave of reducers, which balances load better.

D5. Top 10 products

Records (storeID, productID, amount) from thousands of stores. Output the 10 products with the highest total sales.

Answer
// Round 1 (combiner = reducer) Map1: Emit(productID, amount); Reduce1: Emit(productID, sum) // Round 2 Map2: keep a local top 10 of (product, total); at the end Emit(1, each) Reduce2 (1 reducer): Emit the top 10 of all candidates

The global top 10 must be in some mapper's local top 10, the same intuition as her WordCount 3.

D6. Skewed countries

Web log (timestamp, country, URL). Count visits per country with 4 reducers and hash partitioning. 60% of traffic is from one country. What goes wrong and how do you fix it?

Answer

All of that country's records go to one reducer, which gets at least 60% of the data and becomes a straggler. Fix: a sum combiner, so each mapper sends one count per country and the skew vanishes from the shuffle. Without that, split the hot key (salt it as country#1 to country#k) and add the partial counts in a second round.

D7. Block size

A 640 MB file. How many map tasks with 64 MB blocks and with 128 MB blocks? Which gives more parallelism, and what is the cost?

Answer

640 / 64 = 10 maps. 640 / 128 = 5 maps. Smaller blocks give more parallelism and better load balancing, but each task has setup overhead, so very small blocks waste time. Her slide: maps should take at least about a minute.

D8. Her sort example

Part 1 slide 29: Map is (key, value) → (value, _) and Reduce is identity. What is the result, and why can't you use hashing to partition?

Answer

The values become keys, so the shuffle sorts them and each reducer outputs its values in sorted order. Hash partitioning would scatter neighboring values across reducers, so the files would not concatenate into a global order. A range partitioner (with ranges chosen from the data distribution so reducers stay balanced) gives a total sort. With one reducer, any partitioner works.
